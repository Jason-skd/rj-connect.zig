# 密码学与 V3 摘要

本页定义认证所用的标准密码学原语与锐捷私有构造，其适用范围为本报告所述旧式认证协议。

本页未标记的算法、常量、模式和固定向量属于[第 1 类已证明事实](scope.md#信息分类)。V3 材料是客户端构建或运行进程派生的事实，不是可由 client 任意解释的协议配置。

## 标准原语

协议使用以下公开原语：

| 原语       | 用途                                          |
| ---------- | --------------------------------------------- |
| MD5        | EAP-MD5 proof、口令链、直接通信 authenticator |
| RC4        | 服务器下发 key 与 IV 的解包                   |
| DES-CBC    | SAM/SMP direct payload                        |
| Tiger      | V3 mode 3 和 mode 4                           |
| Whirlpool  | V3 最终摘要                                   |
| RIPEMD-128 | V3 mode 2 和 mode 3 的私有变体基础            |
| SHA-1      | V3 mode 1、2 和 4 的私有变体基础              |

MD5、RC4、DES-CBC、Tiger 和 Whirlpool 使用公开标准定义。私有变体在名称后加 `vz`，例如 `MD5vz`。

## 口令链

口令先转成 GBK，再零填充到 16 字节的整数倍。空口令仍占用一个 16 字节块。

设 `U=username_bytes`，`P=padded_password`，`IV` 为 16 字节起始值。第 `i` 个密文块为：

```text
m0 = MD5(U || IV)
c0 = P0 XOR m0

mi = MD5(U || C(i-1))
ci = Pi XOR mi
```

输出长度等于填充后的明文长度，不把零填充长度作为独立字段发送。

| 路径    | 16 字节起始值            |
| ------- | ------------------------ |
| EAP-MD5 | 服务器下发的 challenge   |
| PEAP    | ASCII `!jierui9002pmsus` |

PEAP 固定起始值长度为 16，不带 NUL。

EAP-MD5 路径在无 challenge 时以 16 个零字节为起始值，即 `c0 = P0 XOR MD5(username_bytes || 0^16)`；收到 challenge 后改用该 challenge 为起始值重算。初始密文由用户名与口令决定，不是构建内嵌常量。客户端在收到 challenge 后保留该密文，后续无 challenge 的 Start、Identity 与 Logoff 帧复用它；观测到部分失败重试回到零 IV 默认值，复位触发条件尚未确定。

2026-10-25 的差分复核在不知道口令的情况下关闭了 IV 问题：同一次认证的 challenge 前值 `pre` 与 challenge 后值 `post` 使用相同口令块 `P0`，于是 `MD5(U || IV_pre) = pre XOR post XOR MD5(U || challenge)`。三份采集的 9 次交换中，3 次 challenge 前默认值与 `MD5(U || 0^16)` 一致；4 组 `pre` 等于上一帧 `post` 的相邻交换，其值与 `MD5(U || 上一次 challenge)` 一致。

>
> TODO（待 client 上线联调）：服务器是否校验 challenge 前帧中的 `0x2f`；将其置零或省略是否仍可通过认证。

## V3 材料

| 信息           | 布局                         |
| -------------- | ---------------------------- |
| 应用数据 `A`   | 目标客户端应用提供的字节串   |
| 动态库数据 `D` | 目标客户端动态库提供的字节串 |

### 应用数据 `A` 的用途

`A` 参与五种 V3 模式的应用程序摘要。它不是 challenge，也不是安装路径字符串。

### 应用数据 `A` 的获取方式

Linux 1.31 和 macOS 1.35 都将 `A` 作为固定字节数组编译进主程序；V3 调用直接复制该数组，不读取外部文件、不选择偏移，也不做额外预处理。

### 动态库数据 `D` 的用途

`D` 与 `A` 共同参与 V3 模式构造。部分模式从 `D` 生成首发摘要，部分模式从 `A` 生成首发摘要。

### 动态库数据 `D` 的获取方式

Linux 1.31 和 macOS 1.35 同样将 `D` 作为固定字节数组编译进主程序，并由 V3 调用直接复制使用。

构建绑定的材料：

| 客户端构建     | 材料 | 长度 | SHA-256                                                            |
| -------------- | ---- | ---- | ------------------------------------------------------------------ |
| Linux 1.31 x64 | `A`  | 1820 | `1cbb02d50abb01e07f83b7dc4adc653c76c581dd53d55b7a4318e57d730c32aa` |
| Linux 1.31 x64 | `D`  | 2035 | `45ce54267c6a831e65dfeb08aad6819cf64e0f8d2c121439f98914b903bb4640` |
| macOS 1.35     | `A`  | 1820 | `4fe311501474b5abbf5bd8d86d174c025bf077d9da1ceb267445c6a54c508a98` |
| macOS 1.35     | `D`  | 2035 | `16d67ee41bde09a6847c53d9817ce1ba4650da1d740157f47f4ccaa2fe8f6068` |

这些材料随客户端构建固定，Linux 和 macOS 的字节内容不同。客户端没有在启动时校验材料版本或摘要；部署选择等价于绑定具体客户端构建。

Windows 6.85 的 EAP-MD5 与 PEAP 使用进程状态派生的 V3 材料：

1. 以进程全局的 16 字节种子为起点。
2. 结合当前进程映像、模块信息与调用方字节。
3. 按种子选择摘要分支，生成 128 字节结果。
4. 分别以 `0x4d 0x80 ...` 或 `0x60 0x80 ...` 发送。

该结果随进程运行状态变化，不属于固定文件或固定数组摘要。Linux/macOS 的 `A`、`D` 材料模型不适用于 Windows 6.85。

目标 macOS 1.35 部署已有三份采集，共提供 9 个 `(challenge, 0x4d)` 对（2026-10-24 两份 7 个，2026-10-25 冷启动 2 个），覆盖 mode `0`、`2`、`3` 和 `4`（未出现 mode `1`）。以 macOS 内嵌的 1820/2035 字节 `A`/`D` 材料按本页五模式构造复算，9 个结果与运行时 `0x4d` 文本逐字节一致；三次采集各有一个成功会话，其响应获得 Success。该部署的 mode 选择与固定材料关系因此已由运行值验证；Windows 的进程派生材料结构仍单独成立。

`0x4d` 在 challenge 之前固定为 128 个零字节；收到 challenge 后才按上表选择 mode 并生成摘要。目标部署的 Start 与 challenge 前 Identity 帧都使用全零值。

> TODO（后续版本可选补齐调查）：Windows 6.85 的运行进程状态到 V3 材料与摘要的完整派生关系需要目标 Windows 运行时抓包，不属于当前版本实践范围；Linux 1.31 与 macOS 1.35 的固定材料构造已按运行值验证。

## 服务器 key 与 IV

服务器字段 `0x5c` 和 `0x5d` 各带 8 字节 RC4 密文。RC4 key 为以下 15 个 ASCII 字节：

```text
com.ruijie.www
```

解密结果分别作为直接会话的 DES key 和初始 IV：

```text
des_key = RC4("com.ruijie.www", field_0x5c)
initial_iv = RC4("com.ruijie.www", field_0x5d)
```

key 与 IV 属于当前 Direct 会话的密钥材料，与对端地址及端口绑定。

## 直接通信保护

direct payload 使用 `des_key` 和 `initial_iv` 执行 DES-CBC。明文先零填充到 8 字节的整数倍，分片发生在加密之后。

每个片段使用原 header 的 authenticator 字段作为 16 个零字节，计算：

```text
MD5(header[0..8] || zero[16] || header[24..42] ||
    encrypted_chunk || des_key || initial_iv)
```

随后把摘要写入 header 的 `0x08..0x17`。接收端完成头和长度校验后，独立验证每个片段。

## MD5vz

`MD5vz` 保留 MD5 的消息分块、轮顺序、移位、标准轮常量和填充，使用不同的初始状态：

```text
A0 = 0x50137246
B0 = 0x8acf9dbe
C0 = 0xc9efaced
D0 = 0x25647013
```

单步形式为：

```text
a = rotl32(a + F(b,c,d) + X[k] + K[j], s)
a = a + b + delta[j]
```

四轮 `delta` 依次为 `2`、`-2`、`-1`、`1`。第三轮中，对标准消息字 `X[6]` 使用的常量改为：

```text
0x04881d05 + ((X[2] >> 8) & 0xff)
```

其余标准轮常量保持不变。末尾按 MD5 规则追加 `0x80`、零和 64 位小端消息位数，输出 16 字节小端状态。`MD5vz` 的十六进制文本为 32 个小写字符。

## SHA1vz

`SHA1vz` 保留 SHA-1 的 80 步结构和消息扩展，使用不同初始状态：

```text
32075416 f8dae9bc 73541260 8acb9dfe fd0c2e1b
```

轮区间与常量如下：

| 轮       | 常量                    |
| -------- | ----------------------- |
| `0..19`  | `-0x5d6aa4d4`           |
| `20..39` | `0x16ae9deb + block[0]` |
| `40..60` | `-0x34032e48`           |
| `61..79` | `-0x5cd39e93`           |

`block[0]` 是当前 64 字节输入块的首字节。第三段包含 21 轮，最后一段包含 19 轮。最终 feed-forward 为：

```text
H0 += A + 1
H1 += B
H2 += C
H3 += D
H4 += E
```

输出为 5 个 32 位状态的大端序 20 字节。

## RIPEMDvz

`RIPEMDvz` 使用 RIPEMD-128 的两条并行线和 128 步调度。非覆盖步骤采用以下轮函数修饰：

| 轮组 | 函数与附加量      |
| ---- | ----------------- |
| 1    | `f1 + 2`          |
| 2    | `f2 + 0x325b99a1` |
| 3    | `f3 + 0x1baed69c` |
| 4    | `f4 + 0xbcdcb1f9` |
| 5    | `f4 + 0x5a82798a` |
| 6    | `f3 + 0x41d42d5d` |
| 7    | `f2 + 0x30ed3f68` |
| 8    | `f1 + 2`          |

初始状态为 `10257436 a8bd9cfe 9efcad8b 12375460`。以下步骤使用额外替代量，`w[i]` 为当前 16 个 32 位小端消息字：

| 轮组   | 索引  | 附加量        |
| ------ | ----- | ------------- |
| 2      | `w4`  | `+2`          |
| 2      | `w3`  | `-0x43234e07` |
| 2      | `w0`  | `+2`          |
| 2      | `w8`  | `+2`          |
| 2 后半 | `w11` | `+0x325b99a1` |
| 2 后半 | `w15` | `-0x43234e07` |
| 2 后半 | `w3`  | `-0x43234e04` |
| 3      | `w6`  | `+0x325b99a1` |
| 3      | `w11` | `-0x43234e06` |
| 4      | `w11` | `+0x325b99a1` |
| 4      | `w3`  | `+0x1baed69c` |
| 4      | `w8`  | `+2`          |
| 4      | `w15` | `+2`          |
| 4      | `w2`  | `-0x43234e04` |
| 5      | `w11` | `+0x325b99a1` |
| 5      | `w15` | `-0x43234e07` |
| 5      | `w3`  | `-0x43234e04` |
| 6      | `w5`  | `-0x43234e07` |
| 6      | `w10` | `-0x43234e03` |
| 6      | `w1`  | `+0x325b99a1` |
| 7      | `w6`  | `-0x43234e02` |
| 7      | `w8`  | `+0x5a82798a` |
| 7      | `w4`  | `+0x41d42d5d` |
| 8      | `w6`  | `-0x43234e02` |

未列出的步骤使用该轮组的函数与附加量。最终混合为：

```text
t7 = wv7 + wv2 + H1
H1 = H2 + wv3 + wv4
H2 = H3 + wv0 + wv5 + 1
H3 = H0 + wv1 + wv6
H0 = t7
```

输出 4 个 32 位状态的小端序 16 字节。

## Tiger 与 Whirlpool

Tiger 使用标准 Tiger，不使用 Tiger2。初始状态为：

```text
158e427ac96b03df f025c13b8e9da784 b690ab45c3e21b74
```

消息按 64 字节分块，填充首字节为 `0x01`，长度字段为 64 位小端。输出 24 字节小端状态。

Whirlpool 使用标准 Whirlpool 轮函数和 S 盒，对 V3 构造输入计算一次，输出 64 字节。V3 字段再把 64 字节转换成 128 个小写十六进制字符。

## V3 选择

challenge 的字节 0 和 3 按有符号 8 位解释。先求和，再转换为无符号 32 位并模 5：

```text
signed_sum = i8(c[0]) + i8(c[3])
mode = u32(signed_sum) mod 5
```

这一步不能直接使用无符号字节相加。例如 `ff ff` 的有符号和为 `-2`，转换为无符号 32 位后得到 mode `4`。

## 五种 V3 模式

设应用数据为 `A`，动态库数据为 `D`，challenge 为 `C[16]`。

mode `0`：

```text
a_text = hex32(MD5vz(A)) || even_challenge_text
d_text = hex32(MD5vz(D)) || odd_challenge_text
input = first_96_bytes(a_text || d_text)
```

`even_challenge_text` 依次编码 `C[0], C[2], …, C[14]`；奇数序列编码 `C[1], C[3], …, C[15]`。每个字节使用 `sprintf("%02x", (u32)(i8)byte)` 的格式：非负字节为 2 位，负字节符号扩展为 8 位。

mode `1`：

```text
SHA1vz(D)[20] || C[0..6] || SHA1vz(A)[20] || C[6..16]
```

mode `2`：

```text
SHA1vz(D)[20] || C[0..6] || RIPEMDvz(A)[16] || C[6..16]
```

mode `3`：

```text
Tiger(A)[24] || C[0..10] || RIPEMDvz(D)[16] || C[10..16]
```

mode `4`：

```text
Tiger(D)[24] || C[0..8] || SHA1vz(A)[20] || C[8..16]
```

mode 1 到 4 的输入长度依次为 56、52、56 和 60 字节。mode 0 的结果固定读取前 96 字节，即使符号扩展使拼接缓冲区更长。

所有模式的最终值为：

```text
v3_digest = lowercase_hex(Whirlpool(mode_input))
```

EAP-MD5 字段 `0x4d` 与 PEAP 字段 `0x60` 都携带这 128 个 ASCII 字符。
