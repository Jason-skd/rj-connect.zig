# 协议文档管理原则

本页与[研究报告入口](index.md)共同规定报告的表达形式。协议信息按确定程度、来源与适用范围分类，字段、状态和算法的定义保留在各自所属章节。

## 信息分类

所有协议信息必须归入以下六类之一。第 1 类沿用现有定义表；其余类别在信息原本所在章节添加标记。

| 分类                                        | 文档形式                                     | 含义                                                                          |
| ------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------- |
| 1. 非常明确的真相                           | 保留现有定义表和堆叠定义                     | 字段布局、编码或固定机制已有明确证据，例如 `0x00 / 6 / 目的 MAC / 以太网地址` |
| 2. 已证明由 client 传入的生成机制           | 先保留原有定义，再补充用途和 client 获取方式 | 信息是什么已经明确，值需要由 client 从运行环境、部署 profile 或用户取得       |
| 3. 不明确的生成机制，属于当前版本实践范围   | `> TODO（当前版本待调查）：...`              | 只知道数据结构中存在该信息，当前版本需要调查                                  |
| 4. 不明确的生成机制，不属于当前版本实践范围 | `> TODO（后续版本可选补齐调查）：...`        | 只知道数据结构中存在该信息，当前版本不实现                                    |
| 5. 明确的生成机制，不属于当前版本职责       | `> TODO （后续版本可选实施）`                | 机制已经明确，属于后续版本可选内容                                            |
| 6. 调查中的偶然线索                         | `> 存疑线索：...`                            | 尚未证明是否成立，不能当作协议事实                                            |

## 放置规则

- 每条信息留在定义它的报文、字段、状态或密码学章节，不集中搬到本页。
- 第 2 类在原有定义之后补充两小节：信息用于做什么，以及当前目标客户端如何取得该信息。
- 第 3、4、5、6 类使用引用语法就地标记，保留对应定义和适用边界；第 5 类仍保留第 1 或第 2 类所需的完整定义。
- 当前版本不实现的协议机制或没有继续调查的线索仍留在原位置，不得静默删除。
- 字段的布局、来源语义和兼容范围分别陈述；已知字节布局不等于已知其生成机制。
