# 锐捷私有字段布局

本页定义锐捷厂商字段的两种容器、客户端字段、服务器字段及 EAP-MD5 固定段。字段有效范围由所属容器的长度确定。

本页未标记的字节布局、定长值和服务器 TLV 属于[第 1 类已证明事实](scope.md#信息分类)。依赖运行环境或学校客户端构建的值属于第 2 类。

## 通用编码

所有多字节整数使用大端序，除非字段说明另有规定。字符串使用 GBK 字节，固定宽度字符串以 `0x00` 补齐。长度字段覆盖其声明的完整字节范围，不包含外层 EAPOL 头和 Ethernet 头。

锐捷厂商号在线上为：

```text
00 00 13 11
```

解析到其他厂商号时必须停止当前厂商段，不得跳过长度继续猜测。

## 紧凑厂商容器

PEAP、无线和部分配置通道使用紧凑容器：

```text
code:u8
value_len:u8
value[value_len]
```

容器总长为 `2 + value_len`。`code=0x00` 或 `code=0xff` 表示终止。读取器在终止码处停止，不保留后续字节。

紧凑容器不重复携带厂商号。它适用于已经位于锐捷外层内的字段流。

## EAP 扩展厂商属性

有线 EAP-MD5 使用扩展厂商属性：

```text
0x1a
total_len:u8
vendor_id:u32be
code:u8
inner_len:u8
value[inner_len - 2]
```

字段长度为：

```text
total_len = 8 + len(value)
inner_len = 2 + len(value)
```

`vendor_id` 固定为 `0x00001311`。`total_len` 必须不超过当前 EAP data 的剩余长度。

## EAP-MD5 私有尾块

有线 EAP-MD5 的私有段不是 EAP 载荷：它追加在 EAPOL body length 与 EAP length 之外，紧跟在已声明的载荷之后。目标部署的 Start、Identity、MD5-Response 与 Logoff 都携带 566 字节尾块；帧长度关系见 [EAPOL 与 EAP 报文](eap.md#eap-md5-私有尾块)。

尾块由 70 字节固定前缀和 496 字节 `0x1a` 包装属性组成。

### 固定前缀

固定前缀为：

| 字段             | 长度 | 说明                               |
| ---------------- | ---- | ---------------------------------- |
| legacy DHCP info | 23   | 厂商号、DHCP 标志、IPv4 参数和 CRC |
| vendor ID        | 4    | `0x00001311`                       |
| program name     | 32   | 样本为 `8021x.exe`，GBK，零填充    |
| version          | 4    | `major, minor, 平台尾字节`；macOS 1.35 为 `1,35,2,2` |
| logoff reason    | 1    | 目标部署 Logoff 帧为 `0x01`；Start/Identity/MD5-Response 常见 `0x00`，首次 Start 亦出现 `0x30`、`0x61`、`0xa3`、`0xf5` 等值并被服务器接受 |
| vendor ID        | 4    | `0x00001311`                                    |
| reserved         | 2    | 目标部署样本为 `01 f0`                          |

legacy DHCP info 在写入尾块前逐字节执行与 15 字节编码块相同的变换：

```text
on_wire = bit_reverse8(decoded ^ 0xff)
```

下表给出变换前的布局：

| 偏移   | 长度 | 字段                      |
| ------ | ---- | ------------------------- |
| `0x00` | 4    | `00 00 13 11`             |
| `0x04` | 1    | DHCP 启用标志，`0` 或 `1` |
| `0x05` | 4    | IPv4 地址                 |
| `0x09` | 4    | 子网掩码                  |
| `0x0d` | 4    | 默认网关                  |
| `0x11` | 4    | DNS                       |
| `0x15` | 2    | CRC-16，大端              |

CRC-16 覆盖前 21 字节，参数为多项式 `0x1021`、初值 `0`、不反射、最终不异或；校验和在变换之前计算。

### 目标部署逐帧观测

目标部署的私有尾块内容随帧变化。以下为采集结论；原始值含会话材料，不在仓库保存：

| 观测项                | 观测结果                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------- |
| `0x4d`                | Start、Identity、Logoff 为 128 个零字节；MD5-Response 为当前 challenge 对应的 V3 摘要          |
| `0x2f`                | 无 challenge 时为当前保留值（初始为零 IV 链结果）；收到 challenge 后重算并保留该 challenge 的密文；MD5-Response 用当前 challenge 计算 |
| `0x62`                | Start、Identity、Logoff 为 `0`；MD5-Response 为 `1`                                            |
| `0x35` 与 IPv6 地址槽 | Start、Logoff 的 count 为 `0` 且地址全零；Identity、Response 为认证网卡当时地址，`0x36` 始终为零 |
| 其余字段              | `0x17`、`0x18`、`0x2d`、`0x39`、`0x54`、`0x70`、`0x6f`、`0x79` 与会话无关或缓慢变化            |

固定前缀中的 legacy DHCP info 在上述四个帧中相同，其 IP、掩码、网关与 DNS 为认证网卡当时的租约事实，传送前经过 property 变换。

2026-10-25 的冷启动复核与差分复算确认：challenge 前的 `0x2f` 是**零 IV 口令链**结果（`P0 XOR MD5(username_bytes || 0^16)`），由用户名与口令决定；收到 challenge 后以 challenge 为 IV 重算，并把结果保留给后续无 challenge 的 Start、Identity 与 Logoff 帧。Start/Identity 尾块按当前状态构造，不是复用上一帧的完整缓冲；其中 `0x2f` 复用保留的链值。观测到部分失败重试回到零 IV 默认值，复位条件尚未确定。

> TODO（当前版本待动态调查）：`0x2f` 保留值复位为零 IV 默认值的触发条件。
>
> TODO（待 client 上线联调）：服务器是否校验 challenge 前尾块中的 `0x2f`、`0x4d`、`0x62`；将 challenge 前 `0x2f` 置零或省略尾块是否仍可通过认证。

### V2 客户端校验值 `0x17`

字段 `0x17` 表示 V2 客户端校验值。MentoHUST 的构造将完整 `8021x.exe` 等分为八段，再与 challenge 组合生成 MD5 文本；这一规则不代表所有锐捷版本的共同机制。

Linux 1.31 的三个主要私有字段序列不包含 `0x17`。macOS 1.35 的一个 EAP-MD5 部署在 Start、Identity、MD5-Response 和 Logoff 中均携带 `0x17`，inner length 为 `0x22`，值为 32 个零字节。二者的发送条件不同。目标部署的 `0x17` 属于[当前版本实践范围](index.md#当前版本实践范围)，其值由 macOS 1.35 的 `GetV2SegmentHash` 固定写成零值。

Windows 6.85 存在 V2 构造：`0x17 0x22` 后接 32 字节摘要文本，摘要输入由八个进程生命周期对象组成，总长为 144 字节。其主要字段序列使用 V3；V2 的实际启用条件尚未明确。

> TODO（后续版本可选补齐调查）：Windows 6.85 的 `0x17` 触发条件及完整生成关系需要目标 Windows 运行时观察，不属于当前版本实践范围。

> TODO（待 client 上线联调）：目标服务器是否要求 `0x17`；省略该字段是否仍能完成认证。

## 客户端紧凑字段

PEAP 和紧凑通道使用以下字段：

| Code   | 字段             | 值布局                                            | 说明                               |
| ------ | ---------------- | ------------------------------------------------- | ---------------------------------- |
| `0x11` | 客户端版本       | `name[32] + major:u8 + minor:u8 + platform[2]`    | 名称样本为 `8021x.exe`             |
| `0x2d` | 适配器 MAC       | `mac[6]`                                          | 认证网卡                           |
| `0x39` | 服务名           | `name[32]`，Windows 另有 64 字节组合形式          | GBK，零填充；空值省略              |
| `0x50` | IPv4 信息        | `ip[4] + mask[4] + gateway[4] + dns[4] + dhcp:u8` | 17 字节值                          |
| `0x54` | 硬盘序列号       | `ascii[n]`                                        | 最长 64 字节                       |
| `0x55` | 安全域           | `ascii[n]`                                        | 可省略                             |
| `0x5f` | PEAP 口令        | 链式 MD5 密文                                     | 固定 IV 为 `!jierui9002pmsus`      |
| `0x60` | PEAP V3 摘要     | 128 字节 ASCII                                    | 与 `0x4d` 使用相同 V3 构造         |
| `0x62` | 安全检查结果     | `ok:u8`                                           | `0` 或 `1`                         |
| `0x63` | DHCP 阶段        | `phase:u8`                                        | `1` 为首次 EAP，`2` 为第二次 EAP   |
| `0x64` | IPD 结果         | `u16be`                                           | Linux/macOS 省略；Windows 条件发送 |
| `0x6f` | 发行版本         | `ascii[n] + 00`                                   | 固定发送                           |
| `0x70` | 操作系统位数     | `bits:u8`                                         | 32 位为 `0x20`，64 位为 `0x40`     |
| `0x76` | 备用 DNS         | `ascii[n]`                                        | 可省略                             |
| `0x79` | 直接通信最高版本 | `version:u8`                                      | 样本为 `2`                         |

`0x63` 的阶段值来自实际进入 DHCP 第二认证的路径；macOS 1.35 的目标 EAP-MD5 成功帧未携带该字段，
不能把 `0x63=1` 当成所有平台首轮响应的固定字段。

Linux 1.31 从当前服务名生成 `0x39`：先把 UTF-8 转为 GBK；仅当结果非空且不等于配置默认值时发送，值固定为 32 字节，不足部分零填充。

macOS 1.35 的非空服务名声明为 `0x39 0x20`，长度为 32 字节。Windows 6.85 的非空服务名使用 32 字节形式，满足附加配置条件时使用 64 字节组合形式；空服务名均省略。固定宽度服务名以零补齐。

Linux 1.31 仅在安全域非空时发送 `0x55`，值为原始字节串，不含固定默认值。Windows 6.85 的主要认证路径不发送 `0x55`，macOS 1.35 同样不发送该字段。

Linux 1.31 与 macOS 1.35 的主要路径不发送 `0x64`。Windows 6.85 在 IPD 客户端检测状态成立时发送：

```text
1a 0a 00 00 13 11 64 04 00 01
```

其中 `total_len=10`，厂商号为 `0x00001311`，inner length 为 `4`，值为 `00 01`。

目标 macOS 1.35 部署在 EAP-MD5 交换中发送 `0x39="students"` 并由服务器接受；同一部署未发送安全域 `0x55` 或 IPD 结果 `0x64`，服务器 Success 也未要求服务切换。`0x39` 的取值来自运行时 profile 的 `service` 字段，属于第 2 类 client 输入。

> TODO（待 client 上线联调）：目标服务器是否接受 `0x39` 的其他服务名，以及实际发送的备用 DNS `0x76` 取值是否影响认证结果。
>
> TODO（后续版本可选补齐调查）：安全域 `0x55`、IPD 结果 `0x64` 及其他可选字段的服务器接受条件与业务语义；目标部署未发送这些字段，不属于当前版本实践范围。

### Client 输入补充说明

以下字段的线上布局见上表。它们属于第 2 类，client 必须提供对应值；无法证明最小必需集合或安全默认值的部分另行就地标记。

#### `0x2d` 适配器 MAC

用途：标识执行 802.1X 认证和 Direct 通信的网卡。

client 获取方式：从所选网络接口读取硬件地址，并保证它与 EAPOL、DHCP 和 Direct 帧使用的源 MAC 一致。

#### `0x4d` / `0x60` V3 摘要材料

用途：生成 EAP-MD5 字段 `0x4d` 或 PEAP 字段 `0x60` 携带的 128 字符 V3 摘要。

client 获取方式：Linux 1.31 与 macOS 1.35 使用对应客户端构建内置的固定数组 `A`、`D`；材料长度及 SHA-256 见[密码学与 V3 摘要](cryptography.md#v3-材料)。

Windows 6.85 的 `0x4d` 与 `0x60` 均由 16 字节运行时种子、当前进程模块信息及其他输入共同派生，结果长 128 字节；不能以固定 `A`/`D` 数组替代。

目标 macOS 1.35 部署累计 9 个 `(challenge, 0x4d)` 运行值已用内置材料复算，全部逐字节一致，覆盖 mode `0`、`2`、`3`、`4`；材料与模式的细节见[密码学与 V3 摘要](cryptography.md#v3-材料)。

> TODO（后续版本可选补齐调查）：Windows 运行时材料与摘要的完整生成关系需要目标 Windows 运行时抓包，不属于当前版本实践范围；Linux 1.31 与 macOS 1.35 的固定材料对应关系已由运行值验证。

#### `0x54` 硬盘序列号

用途：在 EAP 私有字段和 SMP hello 中提供主机磁盘标识。

client 获取方式：从目标客户端所使用的系统盘稳定标识取得。Linux 1.31 使用 `/etc/mtab` 加 SATA IDENTIFY/`HDIO_GET_IDENTITY`；macOS 1.35 使用 `system_profiler SPSerialATADataType`；Windows 6.85 依次尝试系统卷设备信息、`PhysicalDrive` 和 `Scsi`，从 Identify 串号取最多 20 个 ASCII 字节。三者都删除空格、不添加固定前缀，协议字段上限均为 64 字节。完整规则见[SAM/SMP 直接通信](direct.md#client-输入samsmp-初始身份)。

Windows 6.85 的候选磁盘索引为 `0..3`，串号有效长度最多为 20 字节；协议字段上限仍为 64 字节。

#### `0x6f` 客户端发行版本

用途：参与服务器版本协商和客户端识别。

client 获取方式：从目标客户端安装包的版本元数据或发行文件取得，并按字段允许的 ASCII 形式编码。

#### `program name` 与 `0x11` 客户端名称

用途：标识发起认证的客户端程序，并参与服务器侧客户端识别或版本协商。

client 获取方式：从目标客户端安装包的主程序名称和版本元数据取得，按 GBK 或 ASCII 规定编码并执行固定宽度零填充。

- Linux 1.31：固定名称 `8021x.exe`，最多 32 字节；版本默认 `1,30,1,2`，运行上下文可覆盖 major/minor。
- macOS 1.35：固定名称 `8021x.exe`；major/minor 来自客户端配置字段，后两字节固定为 `2,2`。
- Windows 6.85：固定名称 `8021x.exe`；major/minor 来自当前配置对象，后两字节固定为 `1,2`。

发行版本 `0x6f` 也按平台区分：Linux 与 Windows 读取配置 `ReleaseVer`（Windows 6.85 安装配置为 `6.85`），macOS 固定发送 `RG-SU For Mac V1.35` 后接 NUL。`0x70` 在 macOS 根据 64 位内核状态发送 `0x20` 或 `0x40`；Windows 使用 `GetNativeSystemInfo` 的处理器架构判断 32/64 位。`0x79` 在 macOS 固定为 `2`。

各字段及版本值的必需性取决于服务器接受策略。

#### `0x70` OS 位数

用途：向服务器标识客户端运行平台是 32 位还是 64 位。

client 获取方式：读取当前目标进程或操作系统的位宽，映射为 `0x20` 或 `0x40`。

#### IPv6 地址槽

Linux 1.31 的编码器包含三个地址槽：

- `0x35 0x01 count` 先给出地址数量/状态；
- `0x38` 在链路本地槽非零时发送 16 字节；
- `0x4e` 在 ULA 或 global 槽非零时发送 16 字节；
- 至少有一个 IPv6 地址时，`0x36` 固定发送第三个槽；它是枚举过程中最后见到的地址，不保证与前两个槽不同。

Linux 1.31 的静态编码顺序为 `0x35`、`0x38`、`0x4e`、`0x36`。目标 macOS 1.35 部署的实际发送顺序为 `0x35`、`0x36`、`0x38`、`0x4e`。Start 与 Logoff 中三个地址均为全零；Identity 与 MD5-Response 中 `0x38` 与 `0x4e` 为当时的链路本地与 global 地址，`0x36` 仍为全零。顺序与取值按目标部署采集记录，不能由 Linux 静态顺序外推。

用途：向服务器提供认证网卡的 IPv6 地址及数量或状态。

client 获取方式：枚举认证网卡地址，按目标部署顺序保留原始 16 字节网络序地址；当前目标部署的第三槽为全零。

> TODO（当前版本待动态调查）：三个地址槽在客户端内部的枚举与刷新时机，以及第三槽与“最后枚举”的关系。
>
> TODO（待 client 上线联调）：服务器是否校验槽位顺序、第三槽为零或与前两槽重复，以及目标部署的最小必需集合。

#### 目标部署其余字段的取值来源

以下字段尚未在上文单独展开。它们的目标部署取值与来源状态如下：

## 服务器固定段

该固定段位于 EAP Success 的 EAP length 内，起点相对于 Success 的 data（EAP header 之后的字节）。data 的前 6 字节为 `vendor_id:u32be + notification_len:u16be`，随后是 `notification_len` 字节文本；设通知文本长度为 `N`，固定段起点为 `P = 6 + N`。客户端必须按完整 EAP length 接收带私有数据的 Success，不能要求终端长度恰好为 4 字节；这一点与客户端自己把私有尾块放在 EAPOL/EAP 声明长度之外的做法不同。EAP-MD5 Success 消息中的固定结构为：

```text
P + 0x00   vendor_id:u32be = 0x00001311
P + 0x04   opaque[2]
P + 0x06   session_value:u32be
P + 0x0a   opaque[100]
P + 0x6e   service_count:u8
P + 0x6f   service[service_count][32]
```

`opaque` 表示语义未命名的原始字节，其内容不改变后续服务记录的偏移。

服务记录之后有三个固定记录：

| 记录          | 字节                                          |
| ------------- | --------------------------------------------- |
| record 0      | `vendor_id:u32be + kind:u8(=1) + flag:u8(<2)` |
| record 1      | `vendor_id:u32be + kind:u8(=1) + flag:u8(<2)` |
| encoded block | 15 字节，见下节                               |

每个 record 的长度都是 6 字节。`kind` 不是 1 或 `flag>=2` 时，当前帧不包含有效后续字段。

### 15 字节编码块

编码块逐字节执行：

```text
encoded = bit_reverse8(decoded ^ 0xff)
decoded = bit_reverse8(encoded ^ 0xff)
```

解码后的布局为：

| 偏移   | 长度 | 字段                                       |
| ------ | ---- | ------------------------------------------ |
| `0x00` | 4    | `vendor_id:u32be`                          |
| `0x04` | 1    | `code:u8`，样本为 `1`                      |
| `0x05` | 1    | `length:u8`                                |
| `0x06` | 4    | `value_a:u32be`                            |
| `0x0a` | 4    | `value_b:u32be`，业务层按秒解释时乘以 1000 |
| `0x0e` | 1    | `value_c:u8`                               |

普通厂商 TLV 从以下偏移开始：

```text
P + 0x6f + 0x20 * service_count + 0x1b
```

### 目标部署运行值

目标 macOS 1.35 部署已有三次 EAP-MD5 Success（含 2026-10-25 冷启动），结构一致：固定段之前有 6 字节 `00001311 0000`，
按 `P=6+N` 取 `N=0` 时固定段从 `P=6` 起；其 `vendor_id=0x00001311`、`opaque[2]=0x0069`、`session_value=0`、`opaque[100]` 全零、
`service_count=0`；两条记录均为 `vendor_id=0x00001311, kind=1, flag=1`。编码块解码为
`vendor_id=0x00001311, code=0x0a, length=0`，`value_a` 随会话变化，`value_b=20`，`value_c=0`。同一 Success 之后继续携带 `0x3c`、`0x56`、`0x5a`、`0x5b`、
`0x5c`、`0x5d`、`0x5e`、`0x6e`、`0x79`、`0x80` 和 `0x98`；客户端接受该结构。

三份采集的所有 EAPOL 帧都没有出现 `0x53`。opaque 区、两条记录和编码块因此只证明目标部署的实际值及
客户端接受结果，不能证明其他服务器策略下的必需性。

## 服务器驱动的客户端业务

本节定义服务器字段关联的展示、升级、主机检查及 Portal 行为。这些行为不改变 802.1X/EAP 或 Direct 的字节布局；展示或下载失败不表示认证参数失效。

### SSO 与登录 URL

服务器字段 `0x68` 是登录 URL，`0x72` 是可信 URL，`0x77` 是展示策略：

```text
show:u8 || delay_seconds:u16be
```

认证成功后会尝试展示非空 `0x68`。只有当 `0x72` 非空且 `0x77.show == 1` 时才展示可信 URL；`0x77`
延迟值按秒解释，客户端在 Linux 上用 `delay_seconds * 1000` 毫秒设置定时器。Linux 1.31 的展示动作是
在本地消息窗口加入可点击 URL，不会自动把登录状态、令牌或凭据回传到 URL；浏览器导航和会话整合属于
client。字段缺失或 URL 为空时跳过展示。

### 客户端升级

服务器字段 `0x05` 是四字节最新版本值。Linux 1.31 用高 16 位与本地
`major << 8 | minor` 比较，只有服务器版本更大时才进入升级流程；字段 `0x37` 是固定 247 字节的下载
URL 槽，按 NUL 终止文本解释。

Linux 1.31 的下载 URL 仅接受 `http://` 或 `ftp://`，反斜线、空格和 `#` 分别表示为 `%5c`、`%20` 与 `%23`。升级包格式、安装权限、回滚与签名策略不由这些字段定义。

### 主机检查

字段 `0x14` 和 `0x15` 分别控制代理规避和拨号规避，字段 `0x74` 是代理检测类型位图。本机检测结果通过 EAP 私有字段 `0x62` 的布尔值返回。Linux 1.31 的本机检查结果固定为否；macOS 与 Windows 使用各自的平台检查组件。

EAP 与 SAM/SMP 尚无已明确的通用主机进程列表、代理详情或 ACL 规则容器。Linux 1.31 与 macOS 1.35 的 SMP 命令 `0x05`、`0x06` 不解析主机信息载荷；可明确的认证结果为字段 `0x62` 的布尔值。

### Windows Portal

Windows 6.85 的旧式 Portal 使用独立的 HTTP/JSON 交互，不属于 802.1X、SAM 或 SMP。其 HTTP 相对路径为：

```text
eportal/inferface/authAPI/pageInfo
eportal/inferface/authAPI/login
eportal/inferface/authAPI/logout
eportal/inferface/authAPI/getOnlineUserInfo
```

请求与响应使用 JSON，已确认的字段名包括 `portalUrl`、`selfUrl`、`userip`、`userIndex`、`userId`、
`password`、`serviceDefault`、`userAgent`、`result`、`message`、`success` 和
`keepaliveInterval`。具体 Portal 地址、字段组合与服务器响应由部署决定，这些字段不属于 802.1X 厂商属性。

## 服务器字段选择

RADIUS 服务类型决定认证后的会话协议：

| `0x61` 值 | 会话协议 | 直接载荷                           |
| --------- | -------- | ---------------------------------- |
| `9`       | SAM      | 单字节长度 TLV                     |
| `5`       | SMP      | 双字节长度 TLV，命令字在固定头之后 |

缺失 `0x61` 时，三个客户端都在解析服务器字段前把服务类型初始化为 `9`（SAM），只有实际收到
`0x61` 才覆盖该值。服务列表不参与这个默认选择；服务器仍可用 `0x61=5` 显式切换到 SMP。

Linux 1.31、macOS 1.35 和 Windows 6.85 在字段缺失时都使用对端端口 `8080`、本地端口 `80`。`0x6e` 表示本机 Direct UDP 端口，而不是远程业务端口；部署配置可以覆盖回退值。

macOS 1.35 的一个 EAP-MD5 部署使用以下 Success 私有参数：

| 字段   | 值                          |
| ------ | --------------------------- |
| `0x5a` | `53`                        |
| `0x5b` | `202.116.36.42`             |
| `0x5e` | 与 Success 同秒的服务器 UTC |
| `0x6e` | `138`                       |
| `0x61` | 缺失，保持 SAM 默认值 `9`   |

该会话的已知交换中不含 Direct 报文；上述端点值不表示 Direct 会话已经建立，也不构成其他部署的默认值。

## 校验顺序

有效服务器参数满足以下层次约束：

1. 外层厂商号与总长度有效。
2. 通知长度确定的固定段起点有效。
3. 固定段、服务记录与编码块均位于报文范围内。
4. 普通 TLV 的长度与类型约束成立。
5. 必需字段完整且属于同一有效报文。

边界校验失败的报文不构成有效的会话参数集合。

## 未命名字段

服务器 `0x53` 为按 code/length 定位的不透明字段。其业务名称与消费语义尚未明确。

EAP-MD5 固定段的 opaque 区域及两段 6 字节记录具有已知边界与合法性条件，业务名称尚未明确。目标 macOS 1.35 部署已记录这些字段与编码块的实际运行值；`0x53` 在该部署的 EAP-MD5 会话中未出现。
