# 锐捷私有字段布局

本页给出锐捷厂商字段的两种容器、客户端字段、服务器字段和 EAP-MD5 两侧固定段。实现者应先用外层长度完成边界检查，再读取字段值。

本页未标记的字节布局、定长值和服务器 TLV 属于[第 1 类已证明事实](scope.md#信息分类)。依赖运行环境或学校客户端构建的值属于第 2 类。

## 通用编码

所有多字节整数使用大端序，除非字段说明另有规定。字符串使用 GBK 字节，固定宽度字符串以 `0x00` 补齐。长度字段覆盖其声明的完整字节范围，不包含外层 EAPOL 头和 Ethernet 头。

锐捷厂商号在线上为：

```text
00 00 13 11
```

解析到其他厂商号时必须停止当前厂商段，不得跳过长度继续猜测。

## 紧凑厂商容器

PEAP、无线和部分配置通道使用紧凑容器：

```text
code:u8
value_len:u8
value[value_len]
```

容器总长为 `2 + value_len`。`code=0x00` 或 `code=0xff` 表示终止。读取器在终止码处停止，不保留后续字节。

紧凑容器不重复携带厂商号。它适用于已经位于锐捷外层内的字段流。

## EAP 扩展厂商属性

有线 EAP-MD5 使用扩展厂商属性：

```text
0x1a
total_len:u8
vendor_id:u32be
code:u8
inner_len:u8
value[inner_len - 2]
```

字段长度为：

```text
total_len = 8 + len(value)
inner_len = 2 + len(value)
```

`vendor_id` 固定为 `0x00001311`。`total_len` 必须不超过当前 EAP data 的剩余长度。

## EAP-MD5 客户端固定前缀

EAP Response 的 MD5 type data 之后，锐捷 NAS 路径追加以下固定前缀：

| 字段             | 长度 | 说明                               |
| ---------------- | ---- | ---------------------------------- |
| legacy DHCP info | 23   | 厂商号、DHCP 标志、IPv4 参数和 CRC |
| vendor ID        | 4    | `0x00001311`                       |
| program name     | 32   | 样本为 `8021x.exe`，GBK，零填充    |
| version          | 4    | `major, minor, 1, 2`               |
| logoff reason    | 1    | 正常认证通常为 `0`                 |
| vendor ID        | 4    | `0x00001311`                       |
| reserved         | 2    | `0x0000`                           |

legacy DHCP info 的布局为：

| 偏移   | 长度 | 字段                      |
| ------ | ---- | ------------------------- |
| `0x00` | 4    | `00 00 13 11`             |
| `0x04` | 1    | DHCP 启用标志，`0` 或 `1` |
| `0x05` | 4    | IPv4 地址                 |
| `0x09` | 4    | 子网掩码                  |
| `0x0d` | 4    | 默认网关                  |
| `0x11` | 4    | DNS                       |
| `0x15` | 2    | CRC-16，大端              |

CRC-16 覆盖前 21 字节，参数为多项式 `0x1021`、初值 `0`、不反射、最终不异或。

## EAP-MD5 客户端字段序列

固定前缀之后依次追加以下字段。除 `0x76` 可为空外，推荐按此顺序生成，便于兼容旧服务器。

| 顺序 | Code   | 值布局                    | 条件                 |
| ---- | ------ | ------------------------- | -------------------- |
| 1    | `0x18` | `dhcp_auth_enabled:u32be` | 固定发送             |
| 2    | `0x2d` | `mac[6]`                  | 固定发送             |
| 3    | `0x2f` | 链式 MD5 口令密文         | 需要口令时发送       |
| 4    | `0x76` | 备用 DNS 文本             | 非空时发送           |
| 5    | `0x35` | `aux_state:u8`            | IPv6 数量非零时发送  |
| 6    | `0x38` | `ipv6_addr[16]`           | 第一槽非零时发送     |
| 7    | `0x4e` | `ipv6_addr[16]`           | 第二槽非零时发送     |
| 8    | `0x36` | `ipv6_addr[16]`           | 存在 IPv6 时发送第三槽 |
| 9    | `0x4d` | `v3_digest[128]`          | EAP-MD5 固定发送     |
| 10   | `0x39` | `service_name[32]`        | 服务名非空时发送     |
| 11   | `0x54` | `disk_serial[64]`         | 可省略，固定区零填充 |
| 12   | `0x55` | `security_domain`         | 非空时发送           |
| 13   | `0x62` | `security_ok:u8`          | 固定发送             |
| 14   | `0x64` | `ipd_result:u16be`        | 特殊部署可省略       |
| 15   | `0x70` | `bits:u8`                 | `0x20` 或 `0x40`     |
| 16   | `0x6f` | `release:ascii + NUL`     | 固定发送             |
| 17   | `0x79` | `direct_max_version:u8`   | 样本为 `2`           |

V3 摘要与 `0x4d` 的关系见[密码学与 V3 摘要](cryptography.md)。口令字段的 challenge 来源见[认证状态机](authentication.md)。

旧客户端还存在字段 `0x17` 的 V2 客户端校验值。MentoHUST 将其实现为完整 `8021x.exe` 按八段等分后与 challenge 组合的 MD5 文本，但该实现不能用于推断当前锐捷客户端是否发送该字段。

Linux 1.31 保留 `GetV2SegmentHash` 函数，但三个实际私有字段编码器均未调用它。macOS 1.35 的
`EncapRGVerdorSeg:nBufLen:` 方法也只直接调用 V3，但这不是 EAP-MD5 完整组帧入口。2026-10-24 的
macOS 1.35 目标采集在 START、Identity、MD5-Response 和 Logoff 帧中均观察到
`0x17`、inner length `0x22` 和 32 个有效零字节；因此 Linux 与 macOS 不能共享“请求不发送 V2”
这一结论。macOS 的 V2 由独立 EAP-MD5 组帧路径写入，静态检查 `EncapRGVerdorSeg` 的调用列表不足以排除它。

> 当前 Zig 代码暂不实施：V2 字段 `0x17`。

Windows 6.85 另有 V2 构造函数 `0x51a1a0`。它会写入 `0x17 0x22`，随后读取八个进程生命周期对象、构造 144 字节输入并计算 32 字节文本。其生成机制不是固定的 34 个零字节。当前三个主字段编码器（`0x517...`、`0x518...`、`0x51a4e0` 路径）都直接调用 `0x518a30`/`0x51a4e0` 的 V3 路径，未发现对 `0x51a1a0` 的直接调用。

进一步检查未发现指向 `0x51a1a0` 的直接 CALL、数据地址引用或静态函数指针表项，但不能仅凭静态分析排除运行时计算出的目标地址。

> 运行调查（认证期）：认证期记录 Windows 目标会话是否出现 `0x17`；若出现，保存完整 32 字节值和触发上下文，再判断它是否来自目标部署的隐藏/间接路径。静态不能唯一确定，因为当前制品只排除了普通直接调用，目标部署是否触发该函数只能在运行会话中观察。

## 客户端紧凑字段

PEAP 和紧凑通道使用以下字段：

| Code   | 字段             | 值布局                                               | 说明                             |
| ------ | ---------------- | ---------------------------------------------------- | -------------------------------- |
| `0x11` | 客户端版本       | `name[32] + major:u8 + minor:u8 + platform[2]`      | 名称样本为 `8021x.exe`           |
| `0x2d` | 适配器 MAC       | `mac[6]`                                             | 认证网卡                         |
| `0x39` | 服务名           | `name[32]`，Windows 另有 64 字节组合形式             | GBK，零填充；空值省略            |
| `0x50` | IPv4 信息        | `ip[4] + mask[4] + gateway[4] + dns[4] + dhcp:u8`   | 17 字节值                        |
| `0x54` | 硬盘序列号       | `ascii[n]`                                           | 最长 64 字节                     |
| `0x55` | 安全域           | `ascii[n]`                                           | 可省略                           |
| `0x5f` | PEAP 口令        | 链式 MD5 密文                                        | 固定 IV 为 `!jierui9002pmsus`    |
| `0x60` | PEAP V3 摘要     | 128 字节 ASCII                                       | 与 `0x4d` 使用相同 V3 构造       |
| `0x62` | 安全检查结果     | `ok:u8`                                              | `0` 或 `1`                       |
| `0x63` | DHCP 阶段        | `phase:u8`                                           | `1` 为首次 EAP，`2` 为第二次 EAP |
| `0x64` | IPD 结果         | `u16be`                                              | Linux/macOS 省略；Windows 条件发送 |
| `0x6f` | 发行版本         | `ascii[n] + 00`                                      | 固定发送                         |
| `0x70` | 操作系统位数     | `bits:u8`                                            | 32 位为 `0x20`，64 位为 `0x40`   |
| `0x76` | 备用 DNS         | `ascii[n]`                                           | 可省略                           |
| `0x79` | 直接通信最高版本 | `version:u8`                                         | 样本为 `2`                       |

`0x63` 的阶段值来自实际进入 DHCP 第二认证的路径；macOS 1.35 的目标 EAP-MD5 成功帧未携带该字段，
不能把 `0x63=1` 当成所有平台首轮响应的固定字段。

Linux 1.31 从当前服务名生成 `0x39`：先把 UTF-8 转为 GBK；仅当结果非空且不等于配置默认值时发送，值固定为 32 字节，不足部分零填充。

macOS 1.35 的 `GetServiceName:attributeLen:`（`0x100019a3d`）在服务名非空时写 `0x39 0x20`，随后直接复制完整 `strlen` 字节。它始终向调用方报告总长度 `0x22`，但没有把复制长度限制为 32。服务名超过 32 字节时会发生越界或覆盖后续字段，因此确定性实现必须显式拒绝超长值并按 32 字节零填充，而不能复刻该缺陷。

Windows 6.85 的 `GetServiceName`（`0x5195f0`）同样在服务名为空时不发送。服务名和附加配置满足 64 字节组合条件时走 `0x39 0x40` 路径；否则发送 `0x39 0x20` 加最多 32 字节。当前制品不能证明目标服务器是否要求服务名或特定长度。

Linux 1.31 仅在当前安全域字符串非空时发送 `0x55`，值为原始字节串，编码器不提供硬编码默认值。

Windows 6.85 的 `GetSecDomainName`（`0x51a7d0`）固定返回长度 `0`，因此当前主认证编码路径不发送 `0x55`。macOS 1.35 的实际编码器没有安全域字段分支。三平台不能共享一个“必须发送安全域”的假设；服务端消费语义和目标学校策略仍需部署证据。

Linux 1.31 的 `GetIPDClientRunResult` 固定返回零长度，当前主路径不发送 `0x64`。Windows 6.85 会在 IPD 客户端检测状态成立时发送扩展属性：

```text
1a 0a 00 00 13 11 64 04 00 01
```

其中 `0x1a` 是扩展属性，`total_len=10`，厂商号为 `0x00001311`；字段 `0x64` 的 inner length 字段为 `4`，随后两个 value 字节固定为 `00 01`。macOS 1.35 当前编码器没有 `0x64` 分支。服务器消费该结果的具体业务语义仍未知。

> 运行调查（认证期）：认证期逐平台记录 `0x39`、`0x55`、`0x64`、客户端名称/版本和 IPv6 字段的实际出现情况、字节值及服务器后续响应，再用成功/失败对照确认目标最小集合。静态不能唯一确定，因为客户端编码器只规定可选生成条件，项目没有目标服务器策略或接受矩阵。

### Client 输入补充说明

以下字段的线上布局见上表。它们属于第 2 类，client 必须提供对应值；无法证明最小必需集合或安全默认值的部分另行就地标记。

#### `0x2d` 适配器 MAC

用途：标识执行 802.1X 认证和 Direct 通信的网卡。

client 获取方式：从所选网络接口读取硬件地址，并保证它与 EAPOL、DHCP 和 Direct 帧使用的源 MAC 一致。

#### `0x4d` / `0x60` V3 摘要材料

用途：生成 EAP-MD5 字段 `0x4d` 或 PEAP 字段 `0x60` 携带的 128 字符 V3 摘要。

client 获取方式：Linux 1.31 与 macOS 1.35 绑定到具体客户端构建，并把 `A`、`D` 编译为主程序中的固定数组；具体偏移、长度和 SHA-256 见[密码学与 V3 摘要](cryptography.md#v3-材料)。

Windows 6.85 不读取固定 `A`/`D` 数组。`0x4d` 编码器 `0x51a4e0` 和 `0x60` 编码器 `0x518a30` 都把运行时种子 `0x755818`、当前进程模块信息和其他输入交给 `0x5704b0`，再复制 128 字节结果。该材料随运行进程变化，目标客户端构建只能约束生成机制，不能替代运行时值。

> 运行调查（认证期）：认证期记录目标安装包身份、服务器 challenge、V3 mode、Windows 实际 `0x4d`/`0x60` 值及服务器接受结果。静态不能唯一确定，因为学校定制构建未提供，Windows 摘要还依赖目标进程的实际模块状态；采集脚本须在认证帧中同时保存 challenge 与响应。

#### `0x54` 硬盘序列号

用途：在 EAP 私有字段和 SMP hello 中提供主机磁盘标识。

client 获取方式：从目标客户端所使用的系统盘稳定标识取得。Linux 1.31 使用 `/etc/mtab` 加 SATA IDENTIFY/`HDIO_GET_IDENTITY`；macOS 1.35 使用 `system_profiler SPSerialATADataType`；Windows 6.85 依次尝试系统卷设备信息、`PhysicalDrive` 和 `Scsi`，从 Identify 串号取最多 20 个 ASCII 字节。三者都删除空格、不添加固定前缀，协议字段上限均为 64 字节。完整规则见[SAM/SMP 直接通信](direct.md#client-输入samsmp-初始身份)。

Windows wrapper 只接受磁盘索引 `0..3`。当前协议字段长度允许 64 字节，但 Windows 具体串号生成本身最多产出 20 字节。

#### `0x6f` 客户端发行版本

用途：参与服务器版本协商和客户端识别。

client 获取方式：从目标客户端安装包的版本元数据或发行文件取得，并按字段允许的 ASCII 形式编码。

#### `program name` 与 `0x11` 客户端名称

用途：标识发起认证的客户端程序，并参与服务器侧客户端识别或版本协商。

client 获取方式：从目标客户端安装包的主程序名称和版本元数据取得，按 GBK 或 ASCII 规定编码并执行固定宽度零填充。

- Linux 1.31：固定名称 `8021x.exe`，最多 32 字节；版本默认 `1,30,1,2`，运行上下文可覆盖 major/minor。
- macOS 1.35：固定名称 `8021x.exe`；major/minor 来自客户端配置字段，后两字节固定为 `2,2`。
- Windows 6.85：固定名称 `8021x.exe`；major/minor 来自当前配置对象，后两字节固定为 `1,2`。

发行版本 `0x6f` 也按平台区分：Linux 与 Windows 读取配置 `ReleaseVer`（Windows 6.85 安装配置为 `6.85`），macOS 固定发送 `RG-SU For Mac V1.35` 后接 NUL。`0x70` 在 macOS 根据 64 位内核状态发送 `0x20` 或 `0x40`；Windows 使用 `GetNativeSystemInfo` 的处理器架构判断 32/64 位。`0x79` 在 macOS 固定为 `2`。

各目标部署是否要求这些字段及特定版本值仍属于服务器接受条件，不能由单机制品唯一推出。

#### `0x70` OS 位数

用途：向服务器标识客户端运行平台是 32 位还是 64 位。

client 获取方式：读取当前目标进程或操作系统的位宽，映射为 `0x20` 或 `0x40`。

#### IPv6 地址槽

Linux 1.31 的原始 IPv6 输出已经确认，共有三个地址槽：

- `0x35 0x01 count` 先给出地址数量/状态；
- `0x38` 在链路本地槽非零时发送 16 字节；
- `0x4e` 在 ULA 或 global 槽非零时发送 16 字节；
- 至少有一个 IPv6 地址时，`0x36` 固定发送第三个槽；它是枚举过程中最后见到的地址，不保证与前两个槽不同。

macOS 1.35（`0x100019ce0`）与 Windows 6.85（`0x519f50`）使用相同的 `0x35`、`0x38`、`0x4e`、`0x36` 顺序。Linux 地址填充顺序为链路本地 `+0x34`、ULA/global `+0x44`、最后地址 `+0x54`；`GetIPv6Info` 只判断前两个槽是否非零。各槽的服务器业务用途尚未命名，协议实现应保留原始地址，不应自行扩展为“四个固定类别”。

> 运行调查（认证期）：认证期记录三个地址槽的本机来源、原始 16 字节值、发送条件及服务器接受结果。静态不能唯一确定，因为本机地址集合随目标主机和网络变化，服务器是否要求特定槽也只能由目标部署确认。

## 服务器固定段

设通知文本长度为 `N`，固定段起点为 `P = 6 + N`。EAP-MD5 Success 消息中的固定结构为：

```text
P + 0x00   vendor_id:u32be = 0x00001311
P + 0x04   opaque[2]
P + 0x06   session_value:u32be
P + 0x0a   opaque[100]
P + 0x6e   service_count:u8
P + 0x6f   service[service_count][32]
```

实现必须把 `opaque` 区域按原始字节保留。名称缺失不影响服务记录定位。

服务记录之后有三个固定记录：

| 记录          | 字节                                        |
| ------------- | ------------------------------------------- |
| record 0      | `vendor_id:u32be + kind:u8(=1) + flag:u8(<2)` |
| record 1      | `vendor_id:u32be + kind:u8(=1) + flag:u8(<2)` |
| encoded block | 15 字节，见下节                              |

每个 record 的长度都是 6 字节。`kind` 不是 1 或 `flag>=2` 时，当前帧不包含有效后续字段。

### 15 字节编码块

编码块逐字节执行：

```text
encoded = bit_reverse8(decoded ^ 0xff)
decoded = bit_reverse8(encoded ^ 0xff)
```

解码后的布局为：

| 偏移   | 长度 | 字段                                       |
| ------ | ---- | ------------------------------------------ |
| `0x00` | 4    | `vendor_id:u32be`                          |
| `0x04` | 1    | `code:u8`，样本为 `1`                      |
| `0x05` | 1    | `length:u8`                                |
| `0x06` | 4    | `value_a:u32be`                            |
| `0x0a` | 4    | `value_b:u32be`，业务层按秒解释时乘以 1000 |
| `0x0e` | 1    | `value_c:u8`                               |

普通厂商 TLV 从以下偏移开始：

```text
P + 0x6f + 0x20 * service_count + 0x1b
```

## 服务器紧凑字段

以下字段由服务器在 EAP-MD5 固定段之后或 PEAP 隧道内发送：

| Code   | 名称             | 值布局          | 用途             |
| ------ | ---------------- | --------------- | ---------------- |
| `0x05` | 最新客户端版本   | `u32be`         | 升级判断         |
| `0x14` | 代理规避         | `u32be`         | 主机检查         |
| `0x15` | 拨号规避         | `u32be`         | 主机检查         |
| `0x37` | 升级 URL         | `url[247]`      | 客户端升级       |

## 服务器字段选择

RADIUS 服务类型决定认证后的会话协议：

| `0x61` 值 | 会话协议 | 直接载荷                           |
| --------- | -------- | ---------------------------------- |
| `9`       | SAM      | 单字节长度 TLV                     |
| `5`       | SMP      | 双字节长度 TLV，命令字在固定头之后 |

缺失 `0x61` 时，三个客户端都在解析服务器字段前把服务类型初始化为 `9`（SAM），只有实际收到
`0x61` 才覆盖该值。服务列表不参与这个默认选择；服务器仍可用 `0x61=5` 显式切换到 SMP。

Linux 1.31、macOS 1.35 和 Windows 6.85 在字段缺失时都使用对端端口 `8080`、本地端口 `80`。`0x6e` 表示本机 Direct UDP 端口，而不是远程业务端口；部署配置可以覆盖回退值。

当前 rj-connect 的 `20000` 是原型实现默认值，不是原客户端默认值。端口回退、时间戳策略和计数生命周期应形成内部具名 Direct profile。

2026-10-24 的 macOS 1.35 目标 EAP-MD5 Success 观测覆盖了这些默认值：

| 字段 | 目标值 |
| --- | --- |
| `0x5a` | `53` |
| `0x5b` | `202.116.36.42` |
| `0x5e` | 与 Success 帧同一秒的服务器 UTC |
| `0x6e` | `138` |
| `0x61` | 缺失，因而不覆盖 SAM 默认值 `9` |

该部署采集中没有出现发往 `202.116.36.42` 或使用 `138` 端口的 Direct 帧，不能据此声称真实
socket 已启动。其他部署的字段值仍需认证期调查。

## 校验顺序

实现者应按以下顺序解析，避免半更新状态：

1. 检查外层厂商号和总长度。
2. 读取通知长度并定位固定段。
3. 验证固定段、服务记录和编码块边界。
4. 解析普通 TLV，并逐项保存有效字段。
5. 所有必需字段通过后，原子替换当前会话参数。

任一边界校验失败时，不得保留该帧中已经解析出的部分服务器参数。

## 静态调查边界

Windows `ReadRGVendorSeg`（`0x51a860`）的 148 个显式字段分支没有 `0x53` 的专用语义分支。客户端仍按 code/length 跳过一个字段，但静态代码没有给出业务名称或消费值；因此 `0x53` 只能作为服务器不透明字段保留。

EAP-MD5 服务固定段中的两段 6 字节记录和 opaque 区域已经确定边界与合法性条件。现有代码没有给出业务名称；静态调查无法进一步恢复服务器为何下发这些值。

IPv6 的地址来源和线上槽位已经确定；`0x38` 对应链路本地地址，`0x4e` 对应 ULA/global 地址，`0x36` 是最后枚举地址。服务器是否要求某个槽或赋予其他业务含义仍需部署证据。

> 运行调查（认证期）：认证期保存 `0x53`、固定段 opaque 区和两条 6 字节记录的原值，并在不同成功/失败会话中对照服务器行为。静态不能唯一确定，因为客户端只转发这些服务器值，没有显式业务消费者；它们是否必需只能由目标服务器证明。
